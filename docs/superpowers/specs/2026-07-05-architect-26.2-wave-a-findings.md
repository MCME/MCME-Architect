## Task 5: View-distance native equivalent

**Source reviewed:** `ViewDistanceListener.java` (ProtocolLib `PacketAdapter` on `LOGIN`, `UNLOAD_CHUNK`, `VIEW_DISTANCE`) and `ViewDistanceManager.java` (per-player view-distance state + packet senders).

**Current ProtocolLib effects:**
1. `LOGIN` packet, integer index 2 → overwritten with the player's configured view distance at login.
2. `VIEW_DISTANCE` packet, integer index 0 → overwritten with the player's configured view distance at runtime (`ViewDistanceManager.setViewDistance`/`unsetViewDistance`).
3. `UNLOAD_CHUNK` packet → **unconditionally cancelled** whenever the view-distance module is enabled for the player's world — this suppresses all client-side chunk unloads, i.e. "keep chunks loaded" behaviour.

**Native Paper `Player` API surface found** (`javap -cp paper-api... org.bukkit.entity.Player`):
```
public abstract int getClientViewDistance();
public abstract int getViewDistance();
public abstract void setViewDistance(int);
public default int getNoTickViewDistance();
public default void setNoTickViewDistance(int);
public abstract int getSendViewDistance();
public abstract void setSendViewDistance(int);
public default void openSign(org.bukkit.block.Sign);
public abstract void openSign(org.bukkit.block.Sign, org.bukkit.block.sign.Side);
```

**Mapping (Plan 2 spec for the ProtocolLib removal task):**

| Current effect | Native replacement | Status |
|---|---|---|
| `LOGIN` write (view distance at join) | `Player#setViewDistance(int)` | Clean 1:1 swap |
| `VIEW_DISTANCE` write (runtime view distance change) | `Player#setSendViewDistance(int)` | Clean 1:1 swap |
| `UNLOAD_CHUNK` cancel (suppress chunk unloads / "keep chunks loaded") | **None found.** `setNoTickViewDistance(int)` exists but controls server-side simulation/tick distance, not client-side unload suppression — a different mechanism, not a substitute. | **Gap — behaviour change or documented stopgap required.** |

**Sign editor** (separate, not packet-based in the reviewed files but confirmed here for completeness): `Player#openSign(Sign, Side)` exists natively, confirming the design spec's "clean swap" claim for `SpecialBlockSign`/`OPEN_SIGN_EDITOR`.

**Decision:** Two of three view-distance packet effects have a clean native 1:1 replacement. The chunk-unload suppression does not. Plan 2 must either (a) accept the small behaviour change (players' clients may unload distant chunks that were previously artificially kept loaded — likely low player-visible impact since view distance itself is still being set higher via the native calls above), or (b) investigate a documented stopgap (e.g. Paper's chunk-ticket / keep-loaded APIs at the world/chunk level, which is a different API surface than the packet-cancel approach and was out of scope for this jar-level spike). Recorded per the design spec's own accepted-outcomes list (§5.3, §11 risk table) — this is not a new problem, it is the expected/pre-accepted risk materializing as expected.

## Task 6: PluginUtils removal feasibility (`/checknbt` + plotStoring)

### `/checknbt` — NMS use inspection

**Source reviewed:** `ArchitectCommand.java`, `checkNBT` subcommand (line 102) and `getNBT()` helper (line 313).

**What it does:** Op-only command. With no argument, dumps the NBT of the sender's main-hand item; with a player-name argument, dumps NBT for every non-empty-NBT item in that (online) player's inventory. The dump is produced by `AccessInventory.getItemNBT(item).toString()` — a plain human-readable string sent back via chat. Pure read/display, no NMS writes.

**Native 26.x equivalent check:**
```
javap -cp paper-api... org.bukkit.inventory.ItemStack | grep -iE "getPersistentDataContainer|serializeAsBytes|getData\(|toString"
```
Result:
```
public io.papermc.paper.persistence.PersistentDataContainerView getPersistentDataContainer();
public org.bukkit.material.MaterialData getData();
public java.lang.String toString();
public byte[] serializeAsBytes();
public <T> T getData(io.papermc.paper.datacomponent.DataComponentType$Valued<T>);
```
`io.papermc.paper.datacomponent.DataComponentType` and `DataComponentTypes` (the constant registry, e.g. `MAX_STACK_SIZE`, `MAX_DAMAGE`, `DAMAGE`) both exist and are populated. `ItemStack` also exposes `getDataTypes()` (enumerate all data components present on the stack) and implements `DataComponentHolder`.

**Decision: GO.** A native op-readable dump is achievable via `ItemStack.getDataTypes()` (enumerate present components) combined with `ItemStack.toString()` (Paper's `CraftItemStack` implementation already includes a component dump) and/or `getPersistentDataContainer()` for PDC-specific data. This satisfies the plan's decision rule ("a native call can produce an equivalent op-readable dump ... removal is GO"). The exact rendering (native dump vs. reconstructing an NBT-style string) is an implementation detail for Plan 2; either satisfies "GO" per the rule, since dropping the command outright was already an accepted fallback.

### `plotStoring.IStoragePlot` vendoring — **findings differ from the plan's framing**

**Source reviewed (Architect side):** `Clipboard.java`, `CopyPasteManager.java`, `UndoData.java`.
**Source reviewed (PluginUtils side, via a dedicated sub-investigation):** `IStoragePlot.java`, `MCMEPlotFormat.java`, `StoragePlotSnapshot.java`, `MCMEEntityFilter.java`, `InvalidRestoreDataException.java`, `PlotStorageFormat.java`, `LocalTransformation.java`, `EntityTypeUtil.java`, `EmptyStoragePlotSnapshot.java`, `AccessCraftBukkit.java` (in `PluginUtils` repo, checked out at v1.9.1 — one patch behind Architect's `1.9.2` pom pin; `.m2` only caches `1.9.0`/`1.9.1`, so `1.9.2` itself could not be directly inspected, but a patch-level bump is very unlikely to change this structural picture).

**`IStoragePlot` itself is trivially clean:** 4 methods (`getWorld()`, `getLowCorner()`, `getHighCorner()`, `isInside(Location)`), imports only `org.bukkit.Location`/`org.bukkit.World`. Zero PluginUtils-internal or NMS coupling. Confirmed directly by reading the interface source.

**However, the plan's Step 3 asked to confirm "no transitive PluginUtils-internal coupling beyond what can be copied into `architect.util`" — this does NOT hold for the full copy/paste path.** `Clipboard.copyToClipboard()`/`paste()` don't just consume the `IStoragePlot` interface; they call `new MCMEPlotFormat().save(...)`/`.load(...)` to actually serialize/deserialize the plot contents, and **`MCMEPlotFormat` is deeply, load-bearingly coupled to NMS**:

- Imports `com.mcmiddleearth.pluginutil.nms.*` and calls `AccessCraftBukkit`, `AccessNBT`, `AccessWorld`, `AccessCore`, `AccessServer` throughout both `save()` and `load()` — not incidental/dead code, this is how tile-entity NBT (chests, signs, etc.) and entity NBT (item frames, paintings, armor stands) are actually read from and written back into the world, including position/rotation transforms for rotate/flip.
- `AccessCraftBukkit` itself directly imports and casts to `org.bukkit.craftbukkit.{CraftWorld, CraftBlockEntityState, CraftEntity, CraftPlayer}` — real OBC/CraftBukkit-version-coupled internals, not abstracted reflection, and additionally imports `PluginUtilsPlugin`/`Debugable` (other PluginUtils-internal classes).

**Components that DO vendor cleanly as plain Bukkit-API-only source** (independently verified, no PluginUtils runtime/registry/singleton needed): `IStoragePlot`, `MCMEEntityFilter`, `StoragePlotSnapshot`, `EmptyStoragePlotSnapshot`, `PlotStorageFormat` (the interface `MCMEPlotFormat` implements), `LocalTransformation`, `EntityTypeUtil`, `InvalidRestoreDataException`, and `BlockUtil` (a dependency of `LocalTransformation`, also confirmed Bukkit-only).

**The one component that does NOT vendor cleanly:** `MCMEPlotFormat` — the actual save/load engine. Vendoring it would require also porting (or reimplementing from scratch) the `nms` package's CraftBukkit-version-coupled NBT/entity-access shims, which is a materially different and much larger undertaking than "vendor a helper class," and directly reintroduces NMS into Architect — the exact thing the design's "Maven-only, no paperweight" goal is trying to avoid.

**Decision: NO-GO for full PluginUtils removal this release, GO for `/checknbt` alone.**

This splits cleanly along the plan's own decision rule: `/checknbt`'s NMS use has a native/drop option (→ GO, independent of the rest), but the copy/paste engine's NMS use (`MCMEPlotFormat`) has **no native option** (data-component APIs don't cover raw tile-entity/entity NBT placement with rotation transforms) **and no drop option** (copy/paste, undo, and redo are core, non-optional Architect features — dropping the feature to enable a dependency removal is not an acceptable trade here, unlike the op-only debug command). Per the plan's own rule ("Only a hard need for NMS with no native/drop option is NO-GO"), this is exactly that condition.

**Recommended path for Plan 2:** Fall back to the plan's documented fallback — **defer full PluginUtils removal; keep consuming PluginUtils' 26.2 build** for the `plotStoring`/NMS-serialization piece specifically. Optionally (cut candidate, not required): still vendor the other ~64 trivial helper call sites (`NumericUtil`, `FileUtil`, `message.*`, `EventUtil`, `WEUtil`, `LegacyMaterialUtil`, `developer.*`, `confirmation.*`, `BlockUtil`/`VoxelUtil`/`ReflectionUtil`) and the now-confirmed-clean plotStoring supporting classes (everything except `MCMEPlotFormat`), and native-replace `/checknbt` — this shrinks the PluginUtils dependency surface to just `MCMEPlotFormat` (+ its `nms.*` support) without fully removing the dependency, if a partial win is wanted. That decision is Plan 2's to make; this spike's job is only to confirm removal is not fully achievable as originally scoped.

**Additional note (not a blocker, informational):** Architect's `pom.xml` currently pins PluginUtils `1.9.2`, but `.m2` only has `1.9.0` and `1.9.1` cached — `1.9.2` was not resolvable offline during this investigation. Whatever "PluginUtils' 26.2 build" Plan 2 falls back to consuming will need to be resolved/installed regardless of this spike's outcome, same category of blocker as MCME-Connect (Task 1) but not separately gated since PluginUtils removal was already spike-gated here.

## Task 7: WorldEdit 26.2 version

**Checked:** `curl` against `https://maven.enginehub.org/repo/com/sk89q/worldedit/worldedit-bukkit/maven-metadata.xml` (network call succeeded, no offline fallback needed).

**Result:**
```xml
<latest>8.0.0-SNAPSHOT</latest>
<release>7.4.4</release>
```
`7.4.4` is the newest tagged release (cross-checked against the GitHub tags list — no newer tag exists). Its shipped `plugin.yml` (downloaded and extracted directly) declares:
```yaml
version: "7.4.4+1613-f9e033f"
api-version: 1.21.4
folia-supported: true
```
Further check of WorldEdit's own `master`-branch build (`gradle/libs.versions.toml`, fetched live from GitHub) shows other platforms have already bumped to MC 26.2 (`neoforge-minecraft = "26.2"`, `sponge-minecraft = "26.2"`, `fabric-minecraft = "com.mojang:minecraft:26.2"`), but **the Bukkit/Paper platform pin is still `paperApi = "io.papermc.paper:paper-api:1.21.5-R0.1-SNAPSHOT"`** — i.e. even WorldEdit's current unreleased development branch has not yet moved its Paper module to 26.x.

**Decision: BLOCKER.** No WorldEdit release (nor the current `master` branch) targets Paper 26.x yet. This is a genuine "not yet available" finding from a real network lookup, not a guessed version. Per the plan's instruction, this is flagged as a blocker: copy/paste (Architect's own, via `Clipboard`/`CopyPasteManager` — separate from the PluginUtils `plotStoring` engine above) and WorldEdit-selection features that depend on `worldedit-core`/`worldedit-bukkit` are affected. Plan 2 cannot bump these two dependencies past `7.3.0` until EngineHub ships a 26.x-compatible build; recommend keeping the current `7.3.0` pin (`provided` scope, so still resolvable) and re-checking before Plan 2 is finalized, since this is a fast-moving upstream (`maven-metadata.xml`'s own `lastUpdated` timestamp was from the day before this check).
